# Independent recovery journal operations

The adapter `core_apps.common.recovery_postgres.PostgresRecoveryJournal` is optional and has no fallback to the primary database. It implements the software boundary; deploying it does not approve recovery or open company/financial scopes.

1. Provision a genuinely separate PostgreSQL cluster in the approved failure domain with appropriate backups, retention and access control. A second database in the primary cluster is rejected by PostgreSQL system identifier comparison.
2. Create a dedicated LOGIN runtime role. Give credentials through the deployment secret store, not source control or a shared shell transcript. The role must not be superuser, schema owner or table owner and must not inherit mutation privileges.
3. Run `recovery_journal_setup.sql` as the journal schema owner with psql variables `journal_environment` and `journal_role`. The script creates a new schema; it intentionally fails rather than overwriting an existing journal. Its metadata binds the schema to its physical cluster and environment.
4. Grant the application's primary database role read execution of `pg_control_system()` where required by managed PostgreSQL. No write access to primary control data is needed. The journal role receives the corresponding grant from setup SQL. If the managed service cannot expose a verifiable physical cluster identity, this adapter stays unavailable; do not weaken the check.
5. Configure `RECOVERY_JOURNAL_DSN` and `RECOVERY_JOURNAL_ADAPTER`, using TLS and managed secret rotation appropriate to the actual environment. Do not configure a local development DSN in production. Set the matching `RECOVERY_ENVIRONMENT` and retain the existing quarantined control until approved.
6. Run `python manage.py recovery_journal_readiness`. It checks identity, privilege restrictions and the full append chain. It reports pending/unknown operations but does not grant approval or open a scope. Investigate each unresolved operation against its original provider identity. Never truncate/recreate the journal to make the report clean.
7. Restore and reconcile canonical primary records against original independent journal facts. `reconcile_instruction` restores only instruction acknowledgment and explicitly requires domain reconciliation; it cannot invent settlement, payment or inventory success.
8. Attach actual recovery coverage, failure-domain, provider-reconciliation and independent operator evidence to the existing control approval process. Only then may an authorized operator update the appropriate generation/scopes. No deployment in this increment performs that activation.

The append role has SELECT/INSERT access to entries and read-only access to identity. Preparation commits independently before transport. Session advisory locking survives commits and releases on process death. A prepared or unknown operation never automatically sends again. Lock/connection/integrity failure blocks transport. Full-chain verification currently reads all rows; measure retained journal volume and operational latency before production activation. Any future indexing/partitioning must preserve the same no-replay and chain-verification contract.

Local verification uses a separate physical PostgreSQL process/data directory, a restricted role, synthetic transport and a fully isolated primary restore database. It is not a real provider or a production resilience certificate. Configuration remains empty by default.
