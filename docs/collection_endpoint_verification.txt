Collection endpoint integration verification
Date: 2026-10-01

Scope and outcome
The 52 unique method/path operations in collection.json were mapped to source.
47 included operations are wired. Five operations are intentionally excluded:
- GET and PUT /properties/owner/properties/{propertyId}/availability/
- GET /properties/{propertyId}/available_dates/
- GET /profiles/all/ (collection: testing only; user confirmed exclusion)
- POST /auth/users/reset_password_confirm/ (collection: web frontend only;
  user confirmed exclusion)
Paths above omit the common /api/v1 prefix. Duplicate collection examples,
query variants, and trailing slash variants count as one operation.
See collection_endpoint_coverage.csv for source locations and entry points.

Completed behavior
- Collection-aligned refresh, password-reset and homepage routes; explicit
  backend logout; Google login button connected to the existing Google API flow.
- Server-backed editable user profile and privacy/preferences settings.
- Tenant and owner request inbox routes, with existing visits/received routes
  accessible from their home screens and distinct caches.
- Tenant visit details load the request-detail API. Property location, price,
  rental period, bedrooms, owner verification/masked phone, note and existing
  review render only when returned. Server action flags control available actions.
- Cancellation and review submission call the collection endpoints and report
  success only after API success. Reviews submit three criteria; the server
  calculates the overall rating. Property details link to paginated reviews.
- Owner details support both documented routes; accept/reject flags are honored,
  and rejection sends the displayed timing reason.
- Owner calendar no longer links to the excluded availability editor.
- Arabic/English labels and rating direction were checked in rendered previews.

Verification limits
API responses were mocked; no authenticated live backend or native Google OAuth
session was exercised. This verifies source integration and local behavior,
not production readiness. Existing owner request list behavior loads one page;
multi-page owner inbox navigation remains outside this endpoint-wiring change.

Live acceptance checklist
1. Log in with password and Google on configured native builds. Exercise session
   refresh, forgot password and logout; verify failed logout retains the session.
2. Edit tenant and owner profiles, reopen each editor, and verify saved values.
   Toggle each returned preference, reopen settings, and verify persistence.
3. Open tenant requests and home visits. Open rich and sparse visit details;
   verify optional fields, server labels and permitted actions. Cancel from
   list/details; submit three review criteria; reopen to verify saved review.
4. Open property reviews and load another page on a property with enough reviews.
5. Open owner requests and received visits from home. Inspect both detail routes;
   accept/reject a test request, check the displayed rejection reason, and refresh.
6. Retry failed loads and mutations while offline, reconnect, and confirm that
   failure never appears as successful cancellation, review, settings or logout.
7. Inspect network traffic: no requests to any of the excluded operations.
