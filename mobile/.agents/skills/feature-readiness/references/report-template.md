# قالب تقرير الجاهزية

اكتب التقرير بالعربية ما لم يطلب المستخدم لغة أخرى. استخدم الأدلة الفعلية فقط، واحذف الأقسام أو الصفوف غير ذات الصلة بعد توضيح أنها `غير منطبقة` عند الحاجة.

## 1. النتيجة العامة

**الحكم:** `Ready within verified scope` | `Not ready` | `Verification incomplete`

**الأسباب الرئيسية:** لخص أسباب الحكم، وأبرز موانع الإصدار أو فجوات التحقق الحرجة. وضّح أن الحكم مقيد بالنطاق الذي تم التحقق منه ولا يضمن خلو الميزة تمامًا من العيوب.

## 3. رحلة المستخدم الفعلية ونقاط الدخول

بيّن من يستطيع الوصول إلى الميزة، ومن أي شاشة أو رابط، وتحت أي دور أو صلاحية أو علم ميزة أو نكهة. لخّص مسار التنفيذ حتى النتيجة النهائية، واذكر أي جزء لم يمكن إثباته.

## 4. البيانات الوهمية ومصادر الاستبدال

| الحالة | الموقع ومسار التنفيذ | الظهور والأثر | مصدر الاستبدال | تصنيف المصدر |
|---|---|---|---|---|
| بيانات وقت تشغيل / بيانات اختبار مشروعة / لا توجد نتيجة |  |  |  | `Available and ready to integrate` / `Available but requires changes` / `Missing` / `Not verified` |

لا تخترع مصدرًا أو endpoint أو حقول استجابة. إذا كان المصدر مفقودًا، حدد ما يجب أن يقدمه فريق الخلفية أو مالك المتطلبات.

## 6. الاختبارات والفحوص

| الأمر أو الفحص | النطاق ونوع البيئة | النتيجة | نوع الدليل |
|---|---|---|---|
|  |  | نجاح / فشل / `Not verified` مع السبب | mock / خدمة حقيقية / تحليل ساكن / build / فحص يدوي |

اذكر الاختبارات المطلوبة غير الموجودة، والفحوص التي لم تُنفذ، وما يلزم لتنفيذها. نجاح الاختبارات لا يكفي وحده لإعلان الجاهزية.

## 7. التغييرات المنفذة في وضع Fix & Verify

أدرج الملفات والسلوكيات التي تغيرت، والاختبارات المضافة، والنتائج التي حُلّت. ميّز بوضوح بين:

- نتائج تم حلها والتحقق منها.
- نتائج تم حلها لكن تحققها غير مكتمل.
- نتائج أو فجوات ما زالت قائمة.
- إخفاقات موجودة مسبقًا، إن أمكن إثبات ذلك.

في وضع `Review` اكتب: «لم تُعدّل ملفات التطبيق أو الاختبارات أو الإعدادات.»
